# Benchmarks

Use this folder for repeatable local runtime comparisons. Do not compare Wails against an upstream dev-mode shell.

## Wails Phase 1

```sh
bun install --frozen-lockfile
make wails-build
mkdir -p bench/results
SUITE="linux-desktop-$(date -u +%Y%m%dT%H%M%SZ)"
node bench/linux-desktop-benchmark.mjs \
  --app shreyamnotes-wails \
  --runtime wails-webkitgtk \
  --cmd ./dist/shreyamnotes \
  --runs 10 \
  --sample-seconds 10 \
  --suite "$SUITE" \
  --ready-regex 'ShreyamNotes DOM probe.*"rootFound":true' \
  --env SHREYAMNOTES_DEBUG_BOOT=1 \
  --out bench/results/linux-benchmark.jsonl
```

## Synthetic Large Vaults

Generate deterministic vault fixtures with regular markdown notes, wikilinks,
tags, tasks, fenced code blocks, very large markdown notes, and very large code
files. The generator uses only Node built-ins and writes a
`.bench-vault-manifest.json` into the vault root so benchmark JSONL records can
identify the exact fixture.

Small smoke fixture:

```sh
node bench/generate-synthetic-vault.mjs \
  --out /tmp/shreyamnotes-vault-750-large \
  --clean \
  --notes 750 \
  --folders 25 \
  --large-markdown-files 1 \
  --large-markdown-mib 8 \
  --large-code-files 1 \
  --large-code-mib 8
```

Phase 2 stress fixture:

```sh
node bench/generate-synthetic-vault.mjs \
  --out /tmp/shreyamnotes-vault-5000-large \
  --clean \
  --notes 5000 \
  --folders 50 \
  --large-markdown-files 3 \
  --large-markdown-mib 32 \
  --large-code-files 3 \
  --large-code-mib 32
```

For a first run into a non-empty directory that was not generated by this
script, add `--allow-clean-unmanaged` only after verifying the target path. After
that, `--clean` is enough because the manifest marks the directory as a generated
benchmark fixture.

Run Wails profile-cold against the generated vault:

```sh
make wails-build
SUITE="wails-large-vault-$(date -u +%Y%m%dT%H%M%SZ)"
VAULT="/tmp/shreyamnotes-vault-5000-large"
node bench/linux-desktop-benchmark.mjs \
  --app shreyamnotes-wails \
  --runtime wails-webkitgtk \
  --cmd ./dist/shreyamnotes \
  --vault "$VAULT" \
  --scenario large_vault_5000_with_large_files \
  --runs 5 \
  --sample-seconds 20 \
  --suite "$SUITE" \
  --ready-regex 'ShreyamNotes DOM probe.*"rootFound":true' \
  --env SHREYAMNOTES_DEBUG_BOOT=1 \
  --out bench/results/linux-benchmark.jsonl
```

`--vault` sets `ZENNOTES_VAULT_PATH` for each fresh profile run and records the
fixture manifest in the JSONL row. The readiness marker above measures desktop
shell profile-cold startup; the longer `--sample-seconds` window captures vault
load and indexing memory after the shell is ready.

## Headless Visual Check

Use this when desktop screenshot tools are missing or slow. It validates the same React app and Go API router that the Wails shell embeds. It does not capture native Wails window chrome.

Terminal 1:

```sh
make headless-server
```

Terminal 2:

```sh
PWCLI="$HOME/.codex/skills/playwright/scripts/playwright_cli.sh"

bash "$PWCLI" --session shreyamnotes open http://127.0.0.1:8788
bash "$PWCLI" --session shreyamnotes screenshot
bash "$PWCLI" --session shreyamnotes snapshot
bash "$PWCLI" --session shreyamnotes click e54
bash "$PWCLI" --session shreyamnotes screenshot
bash "$PWCLI" --session shreyamnotes console warning
```

Expected evidence:

- the first screenshot shows the onboarding screen
- the second screenshot shows the sidebar/home workspace after `Skip setup`
- console result is `Errors: 0, Warnings: 0`

## Upstream ZenNotes Baseline

Build an upstream packaged ZenNotes baseline outside this workspace or from an isolated copy:

```sh
bun install --frozen-lockfile
# Build the historical upstream package from its own checkout for comparison.
ZEN_EXE="$(find dist -path '*linux-unpacked*' -type f -perm -111 -name 'ZenNotes' -print -quit)"
stat -c '%n %s' "$ZEN_EXE"
du -sb "$(dirname "$ZEN_EXE")"
```

For now, use ZenNotes' upstream runtime scripts for packaged renderer workflow data:

```sh
ZEN_PERF_DESKTOP_APP_PATH="$ZEN_EXE" \
ZEN_PERF_DESKTOP_NOTES=5000 \
ZEN_PERF_RUNS=10 \
ZEN_PERF_REPEAT_TARGET=desktop \
ZEN_PERF_REPEAT_WARM_CACHE=1 \
  bun run perf:runtime-repeat
```

For process-tree startup and memory against the packaged Wails app:

```sh
SUITE="${SUITE:-linux-desktop-$(date -u +%Y%m%dT%H%M%SZ)}"
node bench/linux-desktop-benchmark.mjs \
  --app zennotes-upstream-packaged \
  --runtime upstream-packaged \
  --cmd "$ZEN_EXE" \
  --runs 10 \
  --sample-seconds 10 \
  --suite "$SUITE" \
  --ready-regex '\[zen:perf\] main\.window\.ready-to-show' \
  --env ZEN_PERF=1 \
  --out bench/results/linux-benchmark.jsonl \
  -- --no-sandbox
```

`--no-sandbox` is only for local Linux environments where the upstream packaged app's sandbox helper is not root-owned with mode `4755`.

## Summarize JSONL

Summarize a tagged Wails/upstream packaged run:

```sh
node bench/summarize-linux-desktop-benchmark.mjs \
  bench/results/linux-benchmark.jsonl \
  --suite "$SUITE"
```

The summary table reports the fixture label when present, successful runs,
startup median/p95, ready/max process-count median/p95, and RSS/PSS/USS
max-memory median/p95 in MiB. Use the same `--suite` value for both Wails and
upstream packaged commands when you want a clean side-by-side comparison from an
append-only JSONL file. Different generated fixtures stay in separate rows even
when they share the same suite and scenario name.

## Size

```sh
make wails-size
stat -c '%n %s' "$ZEN_EXE"
du -sb "$(dirname "$ZEN_EXE")"
find dist -maxdepth 1 -type f \( -name '*.AppImage' -o -name '*.deb' -o -name '*.tar.gz' \) -exec stat -c '%n %s' {} \;
```

## Notes

- RSS overcounts shared libraries. Use PSS as the fairer process-tree memory number.
- Linux memory collection starts the app detached, then samples both the descendant tree and every `/proc` process in the launched process group/session. This keeps WebKitGTK helper processes in the Wails total even when they are not visible under the main PID's `children` file.
- Wails executable size excludes system WebKitGTK; the upstream packaged installed size includes its bundled browser runtime.
- First run includes fontconfig, shader, icon, and web-engine cache effects. Keep it, but compare medians across repeated runs.
- True page-cache cold boot requires root-only `drop_caches`; do not mix it with normal profile-cold runs.
